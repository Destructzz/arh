# Архитектура Фронтенда (Гайд для Бэкендера)

Этот документ написан специально для бэкенд-разработчика, чтобы помочь понять, как устроен наш фронтенд на базе **Vue 3, Nuxt 3 и Pinia**. Спойлер: концепции очень похожи на бэкенд, просто называются иначе.

---

## 1. Стек технологий (Аналогии с Бэкендом)

*   **Nuxt 3 (Фреймворк)**: Это аналог твоего **NestJS**. Он предоставляет структуру папок, роутинг (маршрутизацию), конфигурацию и серверный рендеринг (SSR). 
*   **Vue 3 (Библиотека UI)**: Это движок для отрисовки интерфейса. Сюрприз: тут нет классических HTML-шаблонизаторов (как Jinja или EJS), тут компоненты, которые реагируют на изменение данных.
*   **Pinia (Стэйт-менеджер)**: Это аналог **Сервисов (Services / Providers)** в NestJS или глобального кэша. Здесь хранится состояние приложения (например, какие товары сейчас в корзине, авторизован ли юзер) и бизнес-логика (запросы к API).
*   `useFetch` **(Клиент)**: Аналог `axios`, `fetch` или HTTP-модуля. Инструмент Nuxt для отправки запросов к твоему бэкенду.
*   **Tailwind CSS (Стилизация)**: Фреймворк, где мы пишем стили прямо текстом в классах HTML (`class="text-red-500 flex p-4"`).

---

## 2. Структура проекта (`/frontend/app/`)

### `pages/` (Аналог Контроллеров)
Nuxt использует **File-based Routing** (Файловый роутинг). Файлы в этой папке автоматически становятся маршрутами (URL). Тебе не нужно писать `router.get('/cart')`.
*   Файл `pages/index.vue` → URL: `/` (Главная)
*   Файл `pages/cart/index.vue` → URL: `/cart` (Корзина)
*   Файл `pages/shop/[id].vue` → URL: `/shop/123` (Квадратные скобки `[id]` означают параметр пути, как `@Param('id')` в NestJS).

### `layouts/` (Шлюзы / Обертки)
Файл `layouts/default.vue` — это общий "каркас" сайта. Здесь находится Шапка (Header) и Подвал (Footer). Внутри этого лейаута есть тег `<slot />`, куда подставляется содержимое страницы из папки `pages` (в зависимости от URL).

### `stores/` (Аналог Сервисов)
Здесь мы описываем логику работы с данными (Pinia). У нас есть `auth.ts` (Авторизация) и `cart.ts` (Корзина).

## 3. Магия Vue: Реактивность (Как обновляется интерфейс)

В бекенде, чтобы выдать новый HTML, нужно сгенерировать его заново и отправить клиенту. Во Vue всё **реактивно**. 

У нас есть **Реактивные переменные** (`ref` или переменные внутри Store).
Если ты привяжешь такую переменную к HTML, и потом изменишь её значение в JavaScript, **Vue сам незаметно перерисует только ту часть HTML, где она используется**. Никаких `document.getElementById().innerText = ...`.

*Аналогия:* Представь, что переменная — это ячейка в Excel. А HTML — это формула `=A1+5`. Как только ты меняешь A1, формула сама пересчитывается.

## 4. Как проходит один запрос? (Пример: Добавление в корзину)

Давай разберем путь "от клика до моргания корзины в шапке":

1. **Клик в Компоненте (UI)**
   Пользователь на странице `pages/shop/index.vue` кликает по кнопке: `<button @click="cartStore.addToCart(product.id)">`.

2. **Вызов в Сторе (Service)**
   Вызывается функция (Action) `addToCart` внутри `stores/cart.ts`.

3. **HTTP Запрос к твоему API**
   Внутри `addToCart` дергается `useFetch`: 
   `POST http://localhost:3000/api/cart { productId: 123 }`.

4. **Обновление состояния (State Mutation)**
   Твой бэкенд возвращает `201 Created` и актуальный список товаров или добавленный товар. Frontend Store получает ответ и **обновляет свой внутренний массив** `this.items`.

5. **Реактивное обновление UI (Магия)**
   Значение `this.items` в Сторе изменилось.
   *   Страница Корзины подписана на этот массив — она тут же отрисовывает новый товар.
   *   Шапка (`layouts/default.vue`) тоже подписана на переменную `cartStore.totalItems` (которая считается из длины массива). Как только массив изменился, цифра в шапке автоматически меняется с 0 на 1.
   Нам не нужно вручную искать кнопку в шапке и менять там текст!

## 5. Типичный файл `.vue` (Анатомия)

Любой `.vue` компонент (страница или кнопка) состоит из 2 или 3 частей:

```vue
<!-- 1. ШАБЛОН (Аналог View / HTML) -->
<template>
  <div>
    <h1>Привет, {{ auth.user.login }}!</h1>
    <!-- Клик привязан к функции logout() -->
    <button @click="logout" class="bg-red-500">Выйти</button>
  </div>
</template>

<!-- 2. ЛОГИКА (Аналог Controller логики) -->
<script setup lang="ts">
// Подключаем наш сервис (Store)
import { useAuthStore } from '~/stores/auth'

const auth = useAuthStore()

async function logout() {
  await auth.logout() // Вызываем метод в Сторе
  navigateTo('/') // Редирект на главную (аналог res.redirect)
}
</script>

<!-- 3. СТИЛИ (Мы используем Tailwind, поэтому эту секцию обычно не пишем) -->
<style scoped>
/* Локальные стили только для этого компонента */
</style>
```

## 6. Как работают сессии и авторизация?

Исторически SPA (Single Page Applications) любили хранить токены в `localStorage` и отправлять их ручками в заголовках `Authorization: Bearer <token>`.

В нашем проекте мы используем подход **Cookie (credentials: 'include')**.
1. При логине `/auth/login`, твой бэкенд ставит `Set-Cookie` с JWT или сессией. Будь осторожен, куки должны иметь правильные настройки (HttpOnly).
2. На фронте мы указали в запросах `credentials: 'include'`. Это говорит браузеру: "Браузер, прикрепляй ту самую Cookie ко всем запросам на API автоматически!".
3. Фронтенду даже не нужно трогать токен руками. Он просто шлет запросы, а браузер подкладывает куки.
4. Если Cookie устарела, твой бэкенд возвращает `401 Unauthorized`. Фронт (через Store) ловит эту 401 ошибку, стирает локальные данные юзера (`auth.user = null`) и делает редирект на `/auth/login`.

## Резюме для Бэкендера
*   **Где искать дизайн кнопок?** В папке `pages/` (ищи нужный URL).
*   **Где логика API и запросов?** В папке `stores/` (pinia).
*   **Почему переменные сами меняются на экране?** Потому что они реактивные (`ref`, `computed`, или свойства Store).
*   **Как фронт общается с бэком?** Через `useFetch` (аналог axios).
